Appendix G · JavaScript laboratory guide

The laboratories require no previous programming. This guide explains the small JavaScript vocabulary used in the book, the safety limits of the runner, and a disciplined way to turn code output into mathematical evidence.

Read, predict, run, and revise

Begin by identifying the adjustable constants near the top of a laboratory. Write down a prediction before choosing Run: expected sign, rough size, monotonic trend, or limiting behavior. Read text output and axes with their labels, compare them with the chapter calculation, then change one quantity at a time. Reset restores the canonical program; Download saves an independent JavaScript file whose plot calls print coordinate data when run with Node.

A graph is evidence about the sampled values chosen by a program. It does not inspect every real input and cannot prove a theorem by itself. Use the laboratory to find patterns, boundary cases, or counterexamples, then return to definitions and estimates for proof. Record the code, parameter values, units, and comparison standard when reporting a numerical conclusion.

Runner limits and error messages

Each run starts in a disposable isolated frame and stops after three seconds. The runner accepts at most eight plots, one hundred console lines, and two thousand finite coordinate pairs per plot. Network access is blocked. These limits keep an accidental infinite loop or enormous output from taking over the reading page; they are not mathematical constraints on the algorithms themselves.

A syntax error means the program cannot be parsed, often because a bracket, comma, or operand is missing. A runtime error occurs after execution begins, such as referring to an unknown name. A nonfinite plot error usually signals division by zero, an invalid square root or logarithm, or numerical overflow. Inspect the reported expression and its domain instead of deleting the validation check.

A reproducible numerical report

State the mathematical problem, domain, units, method, parameter values, and stopping rule. Include a known exact value, conserved quantity, bracket, residual, or independent method when one exists. Repeat the computation after refining the step and compare at the same physical point. A table of errors is usually more informative than a smooth-looking curve.

Separate four claims: what a theorem guarantees, what the program computes, what the refinement evidence suggests, and what the model assumes about the real system. If these statements differ, that is useful information rather than a defect to hide. Chapter 28 develops this reporting standard into capstone projects.
