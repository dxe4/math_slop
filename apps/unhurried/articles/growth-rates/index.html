Powers and logarithms

For a positive integer n, aⁿ means a multiplied by itself n times. For example, 3⁴=3×3×3×3=81. For a nonzero base, a⁰=1 and a⁻ⁿ=1/aⁿ. A negative exponent describes a reciprocal.

Worked example. With base 3, the logarithm asks which exponent produces a positive input. Since 3⁴=81, log₃(81)=4. More generally, for a positive base b different from 1, log_b(x)=y means bʸ=x, with x positive.

34=81log3(81)=4

Multiplying powers with the same base adds their exponents: 2³×2²=2⁵. For positive inputs, this becomes the logarithm rule log₂(uv)=log₂(u)+log₂(v). It is a rule about a product.

Try one. Find log₂(1/8) and explain the negative sign.

Worked answer

Because 2⁻³=1/2³=1/8, the logarithm is −3. For a base larger than 1, inputs between 0 and 1 have negative logarithms.

Watch the operation. Logarithms do not generally turn a sum into a sum: log₂(2+2)=2, while log₂(2)+log₂(2)=2 happens to agree in this case. Using 2+4 instead gives log₂(6), which differs from 1+2=3 because 2³=8.

How much does doubling cost?

A program can be quick on ten items and hopeless on a hundred. To reason about scaling, count a specified basic operation as a function of input size n. This is a mathematical model: its units might be comparisons, additions, or candidate checks. Calling every counted operation “one unit” does not assert that real hardware executes them in equal time.

Background capsule. The expression n2 means n multiplied by itself; 2n means multiplying 2 by itself n times. A function maps an input size to a count. We compare positive integer sizes and exact counts before using asymptotic notation. A finite table records examples, not behavior at every possible size.

Three exact bills

Worked example. Imagine three procedures. Procedure L inspects each of n entries once and performs exactly n inspections. Procedure Q checks every ordered pair of entries, including self-pairs, and makes exactly n2 checks. Procedure E considers every subset of an n-element set and makes exactly 2n checks. These are deliberately simple models with counts you can derive from their descriptions.

Doubling n doubles L's count, multiplies Q's count by four, and squares E's count: 22n=(2n)2. The table makes the differences visible, but the formulas supply the exact claims.

Why the formulas have those shapes

Claim. For a set with n distinct labelled elements, the number of subsets is exactly 2n. Every element has two independent choices, included or omitted. Encode a subset by an n-bit string, putting 1 exactly where an element is included. This gives a one-to-one correspondence: every subset yields one string and every string yields one subset. There are two choices for each of n bit positions, so the product is 2n. The argument is a complete count, not an extrapolation from the table.

The quadratic count likewise follows from n choices for the first ordered position and n for the second. If the procedure excludes self-pairs, its exact count becomes n(n−1), still close in scale but no longer n2. Be precise about the operation being counted. A faster machine with 1,000 times the throughput gives a factor of 1,000 on a fixed count model; it does not change an exponential count into a quadratic count.

Do the three formulas alone establish a theorem that 2n eventually exceeds every polynomial? That broader claim needs a proof about arbitrary fixed polynomial degree; the table cannot supply it. Here is a narrower, proved comparison: for n≥5, 2n>n2. The base case is 32>25. If 2n>n2 and n≥5, then 2n+1>2n2>(n+1)2, since n2−2n−1>0. Induction proves the stated range.

A failure case for a casual slogan is n=2: 22=22, so “exponential always beats quadratic” is false. A large constant can also make a nominally linear procedure slower on practical sizes. Growth comparisons answer eventual questions only after constants and thresholds are specified.

Worked example: a constant changes the early ranking

Suppose two exact operation counts are A(n) = 100n and B(n) = n², for positive integer sizes. Dividing the inequality 100n < n² by positive n gives 100 < n. Therefore A has the smaller count exactly for sizes above 100; at 100 they tie, and below 100 B is smaller.

For instance at size 20, the counts are 2000 and 400; at size 200 they are 20000 and 40000. Neither observation alone locates every later comparison. The algebra supplies the threshold and its complete range. Calling A linear and B quadratic describes their growth mechanism, while the multiplier 100 still matters to a finite choice between these two operation-count models. Actual running times require further assumptions about what each counted operation costs.

Count what is actually done

1. A routine inspects every unordered pair of distinct people among six people exactly once. How many inspections? Explain why n2 is the wrong exact count.

Hint for question 1

Count ordered choices first and divide by the two possible orders.

Full solution to question 1

There are 6·5=30 ordered distinct pairs. Each unordered pair appears twice, so the routine makes 30/2=15 inspections. The count n2=36 includes self-pairs and double counts each distinct pair.

2. Compare 2n and n2 at n=3 and n=8. Does either check prove the inequality for every larger n?

Hint for question 2

Calculate both columns; distinguish a checked input from an induction step.

Full solution to question 2

At 3 the values are 8 and 9, so the exponential count is smaller. At 8 they are 256 and 64, so it is larger. Neither isolated check proves a universal later claim. The induction argument above supplies that proof for all integers n≥5.

Model the right operation

Linear, quadratic and exponential counts describe different scaling mechanisms. Exact combinatorial arguments justify these model counts, while measured wall time needs additional hardware and implementation assumptions. The article has proved a particular eventual inequality, not a universal runtime ranking among programs. Big O makes eventual upper bounds precise, including the constants that a growth slogan usually hides.
