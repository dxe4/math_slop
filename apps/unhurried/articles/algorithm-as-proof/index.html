Functions and composition

A function assigns exactly one output to each allowed input. Its domain is the set of allowed inputs; its codomain is the declared set containing the outputs. Different inputs may share an output. For f(x)=x² on the real numbers, both 2 and −2 produce 4.

Worked example. Let f(x)=2x+1 and g(x)=x². The expression f(g(3)) first applies g to 3, producing 9, and then applies f to 9, producing 19. Composition writes this as (f∘g)(3).

f(g(3))=f(9)=19

For a composition to be defined, the output of the inside function must be an allowed input for the outside function. Here both functions accept every real number, so that condition holds.

Try one. Compute g(f(3)). Does changing the order preserve the result?

Worked answer

First f(3)=7, then g(7)=49. This differs from f(g(3))=19. Composition generally depends on its order; the circle symbol names the operation, rather than promising that the two orders agree.

Watch the notation. In f(3), the parentheses name the input to f. They do not mean f multiplied by 3. Read the expression from the inside out.

A recipe that earns its name

Suppose a library has an unordered stack of returned books and wants to find every copy with a given identifier. “Look until you find it” is incomplete: it may miss a later copy, and if none is present it gives no stopping condition. An algorithm needs a defined input, a defined output, finite steps, and a claim relating them. Here the input is a finite list of identifiers and a target; the output can be the list of all matching positions.

Background capsule. A finite sequence has entries numbered 0 through n−1. A function associates an output with each permitted input. A precondition says which inputs are allowed; a postcondition says what the output guarantees. We will assume identifiers can be compared exactly and the input list does not change during a run. These assumptions are part of the specification, not hidden conveniences.

Trace a complete scan

Worked example. Consider the list [A, B, A, C] and target A. Start with an empty output list and an index i=0. At each step, compare entry i with A, append i if equal, and increment i. Stop when i=4. The successive output lists are [], [0], [0], [0,2], [0,2]. The final result [0,2] refers to positions, not copies of the letter. If the target were D, the same scan would stop and return [].

A trace is useful evidence about one run. It is not a proof that every finite list is handled correctly. To make the algorithm precise, include the instruction to stop at i=n before reading an entry. Otherwise the program might access an undefined position. The mathematical specification is “return exactly the indices whose entries equal the target,” not merely “return some match.”

A loop invariant does the proof work

Claim. For every finite input list of length n, the scan stops after exactly n comparisons and returns all and only matching indices. After i iterations, maintain the invariant: the output contains exactly the matching positions among 0,…,i−1. Initially i=0 and there are no inspected positions, so the empty output satisfies the claim. In the next iteration, the test at position i either appends that index if it matches or leaves the output alone if it does not. Both choices make the invariant true for the longer inspected prefix. This proves preservation without assuming the final answer.

Termination requires a separate argument. The nonnegative integer n−i decreases by one on each iteration and cannot decrease forever while remaining nonnegative. At i=n, the invariant covers every valid position. Thus the postcondition follows. The mathematical core is a bounded loop; an actual implementation must additionally handle practical details such as memory limits and identifier equality. Those details do not make the abstract proof false, but they narrow where it applies.

A tempting “optimization” is to stop at the first A. That procedure meets a different specification, finding one witness, but it fails the present one on [A,B,A,C]. A successful trace on [B,A,C] would not expose the error. Correctness always refers to a stated contract; the same code can be correct for one contract and incorrect for another.

A(x)=y

Worked example: an empty input still has an answer

Run the same scan on the empty list, searching for A. Its length is zero, so the initial state has i = 0 = n. The stopping condition holds before any entry is inspected. Return the empty output list. This is correct because there is no valid position at which a match could occur, and it uses exactly zero comparisons.

Now compare a one-entry list [A]. The initial stopping test fails, the comparison at position zero succeeds, and the output becomes [0]. Incrementing the index gives i = 1 = n, so the run ends. Writing the stop test before the access handles both sizes with one rule. An algorithm that assumes a first element exists would have an unstated nonempty-input precondition and would not meet our original contract.

Two specification checks

1. Run the scan on [7,4,7,7] with target 7. State its output and the invariant after two iterations.

Hint for question 1

After two iterations only positions 0 and 1 have been examined.

Full solution to question 1

The output changes from [] to [0], stays [0], then becomes [0,2] and [0,2,3]. At i=2, the matching positions in the inspected prefix [7,4] are exactly [0], so the invariant holds. The final output is [0,2,3].

2. Replace “increment i” with “increment i only after a match.” Give a failing input and explain which proof obligation breaks.

Hint for question 2

Place a nonmatching entry at position zero.

Full solution to question 2

With list [B] and target A, the first comparison fails, i remains 0, and the loop repeats forever. The measure n−i no longer decreases, so termination is unproved and in fact false. The output may remain empty, but a correct answer never arrives.

What the proof bought us

A finite algorithm is more than a plausible recipe. Its contract says what an answer means; an invariant links each intermediate state to that contract; a decreasing measure establishes a finish. For this scan, those ingredients prove a full result for every finite list under exact comparisons. They do not prove that arbitrary programs terminate. If you want a sharper cost question, binary search studies how an additional sortedness precondition can save comparisons.
