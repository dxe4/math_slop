Could a checker foresee every stop?

A program reviewer might wish for a perfect tool: provide any program and input, and it answers whether that run eventually stops. We can test a particular program for a long time, but “not stopped yet” never settles what happens later. The halting problem asks whether a single algorithm could always settle every case. The answer is no, under a standard model of programs that can encode and run other programs.

Background capsule. A program is a finite description interpreted by a fixed universal computational model. It can receive a finite input, halt with an output, or continue forever. Its description can itself be encoded as input data. A decider is an algorithm that halts on every valid input and returns the correct yes/no answer. We will reason by contradiction: assume such a decider exists, build a program from it, and derive incompatible answers on one input. This argument concerns all encoded programs in the model, not whether a particular everyday script has an obvious stopping condition.

Make the hypothetical checker precise

Worked example. Suppose H(P,x) always halts and returns YES exactly when program P eventually halts on input x. Its answers are required to be correct even when P receives its own code. Define a new program D(y): ask H(y,y); if the answer is YES, loop forever; if the answer is NO, halt immediately. The definition is a finite procedure if H exists. Its only potential endless behavior is the deliberately chosen loop.

This table describes D's code; it does not simulate an infinite run to completion. The critical input is D's own finite description. The ability to encode and pass program descriptions makes that substitution legal.

The diagonal contradiction

Theorem, scoped to the stated universal-program model. No total algorithm H correctly decides, for every encoded program P and input x, whether P halts on x. Assume H exists. Run D on its own description. If H(D,D)=YES, the definition of D makes D(D) loop forever, contradicting H's YES. If H(D,D)=NO, D(D) halts immediately, contradicting H's NO. H must return one of the two answers because it is total, and both lead to contradiction. Therefore the assumed H cannot exist.

This is a complete contradiction argument given the machine-model assumptions that programs have finite encodings, can inspect encoded programs as data, and can implement the simple branch and loop used by D. A formal text can encode these operations in a Turing machine or equivalent universal language. We have not proved universality of a particular programming language here. The Church–Turing thesis is a separate claim connecting informal effective computation with a formal model; the diagonal theorem is a mathematical result within the chosen model.

The theorem is about one algorithm that works for every program-input pair. It does not prevent useful analyzers from deciding special families. A loop that decrements a nonnegative counter until zero can be proved to terminate; a program that immediately prints and exits plainly halts. A checker may also answer “unknown” on hard cases, but then it is not the promised total yes/no decider. This distinction prevents the impossibility result from being mistaken for a claim that no termination proof is ever possible.

For a concrete failed shortcut, suppose we run P for a million steps and label it nonhalting if it has not stopped. A program that waits a million and one steps before halting refutes that rule. Increasing the timeout merely moves the counterexample. This finite observation cannot certify nontermination for arbitrary code.

Check both branches

1. Suppose an alleged H answers YES to H(D,D). State the exact contradiction without appealing to a simulation.

Hint for question 1

Read the YES branch of D's definition and compare it with what YES is supposed to mean.

Full solution to question 1

YES asserts that D eventually halts on input D. But D is defined to enter an endless loop whenever H answers YES on that self-input. Thus D(D) does not halt, so H's YES is incorrect. The contradiction comes from the definition, not from waiting for the loop to finish.

2. A program checker always halts and returns HALTS, LOOPS, or UNKNOWN. Does the theorem prohibit it? Explain with the scope of the theorem.

Hint for question 2

Compare its possible outputs with a total correct yes/no decider.

Full solution to question 2

No. The theorem rules out a checker that gives a correct HALTS or LOOPS answer for every pair. A checker that sometimes says UNKNOWN does not meet that promise. It may be useful if every definite answer is sound, but the diagonal proof forces an all-case yes/no promise to fail.

A limit with a boundary

The self-application construction defeats a universal halting decider because its output is designed to disagree with the checker on the diagonal input. It says nothing against proofs for specific programs or conservative tools with an unknown result. This is a logical impossibility theorem about computability, separate from the question of how quickly solvable problems can be handled. P versus NP asks one such efficiency question and remains open.
